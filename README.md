# Kiosco POS 2.4

## Configuración inicial (obligatoria)

1. Firebase Console → proyecto `kiosco-app-15942` → Authentication → Sign-in method → habilitar Email/Password. En Users, crear `admin@kiosco.com` con la contraseña inicial acordada (no se incluye en el código). Cambiarla por una fuerte antes de producción. No existe registro público desde la app. Cada persona debe tener su propio usuario.
2. Firestore Database → crear base en modo producción → Rules → publicar el archivo `firestore.rules`. El navegador nunca escribe directamente; la función Netlify usa el SDK Admin y valida el token de Firebase Authentication, los permisos y la operación.
3. Firebase Console → Project settings → Cloud Messaging → Web Push certificates → Generate key pair. Copiar la **clave pública** a `VITE_FIREBASE_VAPID_KEY` en Netlify. Habilitar Firebase Cloud Messaging API y, si corresponde, FCM Registration API.
4. Project settings → Service accounts → generar una clave privada de la cuenta de servicio (o usar una cuenta de servicio dedicada con permisos de Firestore, Firebase Auth y FCM). Copiar el JSON completo a la variable **privada de Functions** `FIREBASE_SERVICE_ACCOUNT_JSON` de Netlify. Nunca subir la clave a GitHub ni colocarla en una variable VITE_. No enviar el archivo por chat. Mantenerlo protegido y rotar si se expone.
5. Crear repo privado `rpmartinrodriguez/kiosco-pos`. Extraer el ZIP y subir el contenido, incluyendo `netlify/`, `public/`, `.gitignore` y `netlify.toml`, sin incluir credenciales. Importar el repo desde Netlify, rama `main`; build `npm run build`, publish `dist`, Functions `netlify/functions`. Node 22. `ADMIN_EMAIL` es opcional, por defecto `admin@kiosco.com`. Las variables VITE_ se necesitan durante Build; la cuenta de servicio solamente durante Functions. Volver a desplegar tras configurar variables. Agregar el dominio Netlify a Authentication → Settings → Authorized domains.
6. Entrar en la web HTTPS y en Configuración → Notificaciones push → Activar → Probar. Activar por separado en cada dispositivo. En iPhone/iPad: iOS 16.4+ y agregar la web a la pantalla de inicio antes de activar. Cerrar sesión desregistra el dispositivo; mantener la sesión iniciada si se desean alertas en segundo plano. La prueba debe hacerse en un dispositivo real.

## Usuarios y datos

El administrador inicial se identifica por el email configurado. En Configuración → Usuarios y permisos → Agregar usuario, puede crear una cuenta de Firebase Authentication y su perfil asociado en `users/{UID}`. Los roles disponibles son `admin` (Administrador: acceso completo) y `cashier` (Cobrador: Mostrador y Stock, con carga de productos, precios, movimientos de inventario, ventas, apertura y cierre de caja). El rol histórico `manager` se interpreta como Cobrador. El Cobrador no puede acceder a la configuración, estadísticas, historial general de cajas ni registrar ingresos/retiros de efectivo. Los movimientos de stock visibles para cobradores se limitan a los últimos 200; administración conserva el historial completo. Todas las acciones guardan UID, correo y nombre autenticado. No compartir la misma cuenta si se necesita identificar a cada persona. La cuenta de servicio necesita permisos para crear usuarios de Firebase Auth además de los permisos existentes.

El stock se registra en unidades individuales. Para compras por pack, el servidor divide el costo por las unidades por pack y multiplica la cantidad de packs por las unidades por pack. Al reponer stock puede indicarse opcionalmente el costo de compra por presentación; se actualizan el costo unitario y el precio sugerido con el recargo existente y redondeo a centenas. Las ventas nuevas aceptan Efectivo y Mercado Pago, individualmente o combinados; los informes históricos conservan los medios anteriores. El dinero recibido en efectivo y el vuelto no alteran el importe neto registrado en caja.

Colecciones: `products`, `barcodes`, `sessions`, `sales`, `stockMoves`, `cashMoves`, `meta/cash`, `audit`, `pushTokens`, `users`. Se crea una caja compartida con bloqueo transaccional, no una caja por terminal. Los documentos se crean al operar. No se importan automáticamente los datos locales de v1. No hay restauración desde el navegador. Una venta y su descuento de stock se guardan en una sola transacción; el servidor calcula el total con precios vigentes y verifica pagos. El identificador de solicitud evita duplicados mientras se reintenta una misma operación en la misma pantalla; no reemplaza una conciliación después de recargar o perder conexión.

## Push y auditoría

FCM se envía desde Netlify tras confirmar la operación. Se alerta por apertura/cierre de caja, ingreso/retiro de efectivo, alta de producto, cambio de costo/precio/margen, ajustes manuales de stock y ventas registradas con Mercado Pago (incluidas las combinadas con efectivo). Las ventas en efectivo y el descuento automático de stock se auditan, sin push por cada descuento. En Notificaciones se muestran las últimas 100 operaciones y estado de despacho. La entrega de FCM no confirma que el dispositivo haya mostrado el mensaje. Si FCM falla, la venta sigue registrada y queda el estado del envío en auditoría; no se ha implementado reintento automático persistente. El cobro digital se registra manualmente: no verifica acreditaciones de Mercado Pago (se requerirían API y webhook). Los datos sensibles de notificaciones pueden mostrarse en pantalla bloqueada según la configuración del dispositivo.

## Validación y límites

Sintaxis JavaScript revisada; cálculo de packs, formato argentino y medios de pago comprobados mediante pruebas unitarias simples. No se han instalado dependencias ni ejecutado build en el entorno de generación por falta de acceso al registro npm. No se ha probado conexión a Firebase, despliegue, lectores o FCM en dispositivos reales. Validar todo antes de utilizar con ventas reales. La interfaz consulta inventario e historial completo al iniciar y al actualizar después de cambios; antes de escalar a un kiosco de alto volumen, implementar paginación y sincronización incremental para reducir lecturas. Las reglas cerradas requieren usar las Functions; `npm run dev` por sí solo no sirve para probar API. Usar `netlify dev` con variables configuradas o un deploy de prueba. No hay soporte offline de ventas, facturación fiscal ni conciliación bancaria.

## Versión 2.2

- Menú lateral desplegable, formulario por etapas, precio sugerido editable y reposición con aviso de aumento del costo unitario. El historial por producto consulta los eventos de alta, modificación, reposición y ventas, incluidos registros previos disponibles en auditoría y stockMoves. No se reconstruyen eventos que nunca fueron registrados.
- Historial de cajas agrupado por día de apertura y filtros por fechas y operador; ranking por cantidad y estadísticas por hora real de venta en horario argentino. Mercado Pago/transferencia incluye los medios digitales históricos; el detalle conserva todos los medios originales.
- El administrador puede asignar contraseñas temporarias, tanto al crear una cuenta como al recuperarla. Se bloquean todas las operaciones del usuario hasta que elija una contraseña distinta, verificando la temporal en el servidor. Se revocan sesiones anteriores y se eliminan los tokens push del usuario al restablecer la contraseña. Si una operación de autenticación se interrumpe entre Firebase Auth y Firestore, el administrador debe repetir el restablecimiento después de un minuto (o usar la consola de Firebase y corregir el perfil si el administrador principal quedó bloqueado). No se guardan contraseñas en texto plano ni en auditoría. Se requiere permiso de Firebase Admin para actualizar usuarios y revocar sesiones. No es recuperación por correo: los correos internos pueden ser ficticios.

## Versión 2.3

- Contraste aumentado en paneles, tablas, formularios y totales. Los campos numéricos usan formato argentino en vivo, con punto de miles y coma decimal; los códigos de barras permanecen como texto sin formato.
- Categorías: se sugieren las categorías existentes de productos y el servidor reutiliza una etiqueta canónica por clave normalizada (mayúsculas, tildes y espacios). `categories` se crea automáticamente al guardar; no se reescriben categorías históricas ni se fusionan sinónimos o plurales distintos.
- La campanita de administración abre las últimas 100 notificaciones de eventos y guarda el estado leído/borrado por UID en `notificationReceipts`; `notifications` se crea automáticamente con las nuevas operaciones. Los eventos anteriores disponibles se recuperan de las últimas 100 entradas de auditoría. Borrar una notificación no elimina auditoría, ventas ni stock, ni afecta la bandeja de otros administradores. La campanita se actualiza al abrirla, iniciar sesión, actualizar la app, regresar a la pestaña o recibir push en primer plano. No agrega polling continuo. No se necesitan nuevas reglas ni variables.

## Versión 2.4

- Alta y edición de productos en una vista amplia de tres columnas en escritorio, con resumen de compra, stock y precio editable visibles juntos. En pantallas estrechas o de altura insuficiente se reorganiza y permite desplazamiento con acciones inferiores accesibles; no se ocultan campos obligatorios.
- Alta, edición y reposición admiten precio de compra con IVA incluido (predeterminado para productos existentes sin datos de IVA) o sin IVA. En este último caso se suma 21% y se redondea el importe de compra por presentación a centavos antes de dividir por unidades y aplicar el recargo y redondeo a centenas. El servidor repite el cálculo y guarda el costo final unitario, la condición ingresada, el importe de compra y el importe final por presentación. Los costos anteriores no se migran ni se incrementan automáticamente. El IVA es un componente del costo según la modalidad solicitada, no un cálculo fiscal de crédito o débito de IVA.
- No requiere cambios en las reglas ni variables existentes. Pruebas de cálculo y sintaxis realizadas; queda pendiente verificar el ajuste visual en los tamaños reales de pantalla y la integración en Netlify/Firebase.
